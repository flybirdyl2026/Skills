# 接口测试用例设计规范

> 本文档定义接口测试用例的命名、字段、类型、数量分配、预期结果撰写、业务流程串联等规则。SKILL.md 在"设计用例"步骤时引用本文件。

---

## 一、接口定义规范

### 1.1 命名规范
| 项目 | 规则 | 示例 |
|------|------|------|
| 接口名称 | 取 Apifox Summary 中的接口中文名称 | `查询文件关联列表` |
| 请求方法 | 全大写，对应 RESTful 语义 | `GET` `POST` `PUT` `DELETE` |
| 路径命名 | `/资源/子资源`， kebab-case | `/server/file-info/page` |
| 参数命名 | 驼峰或下划线，全项目统一 | `pageNum` 或 `page_num` |

### 1.2 参数规范
- **必填 / 可选** 必须明确标注，使用 `required: true/false`
- **参数类型** 需声明：`string / number / boolean / array / object`
- **格式约束** 需注明：字符串长度、数值范围、枚举值列表、正则表达式
- **默认值** 有默认值时注明，便于缺省测试
- **中文 / 特殊字符** 统一 UTF-8 编码

## 二、接口测试类型

### 2.1 按测试目标分类

| 类型 | 目的 | 关注点 |
|------|------|--------|
| **功能测试** | 验证接口是否按需求正常工作 | 输入→输出正确性、业务逻辑 |
| **边界测试** | 测试极端值和临界条件 | 空字符串、最大长度、负数、0、最大分页 |
| **鉴权测试** | 验证身份校验是否生效 | appCode有效/无效/过期、无token |
| **参数校验测试** | 验证参数合法性校验 | 缺参、类型错误、格式错误 |
| **业务场景测试** | 验证多接口串联的业务流程 | 增→查→改→删链路 |
| **安全测试** | 验证敏感数据保护和注入风险 | SQL注入、XSS、越权访问 |
| **错误处理测试** | 验证异常情况处理 | 网络超时、服务不可用、非法输入 |

### 2.2 按测试方式分类

| 类型 | 说明 | 适用阶段 |
|------|------|---------|
| **单接口测试** | 独立验证每个接口的正向/逆向输入 | 全阶段 |
| **链路测试** | 从用户视角串联多个接口完成业务场景 | 集成测试阶段 |
| **冒烟测试** | 少量核心用例快速验证服务是否可用 | 上线前快速验证 |
| **回归测试** | 每次变更后重复执行，防止引入新问题 | 持续集成 |

## 三、测试用例设计规范

### 3.1 用例命名结构
```
[模块名]_[功能点]_[前置条件]_[预期结果]
```
示例：`文件管理_删除文件_文件存在_返回200并删除成功`

### 3.2 用例 JSON 字段规范（cases/*.json）

用例文件中的每个用例对象必须包含以下字段：

| JSON 字段名 | 说明 | 示例 |
|------------|------|------|
| `case_id` | 用例唯一编号 | `TC001` |
| `api_name` | 接口中文名称（与 Apifox summary 对齐） | `创建订单` |
| `method` | 请求方法 | `GET` / `POST` / `PUT` / `DELETE` |
| `path` | 完整路径，含 `{uuid}` 等 path 参数占位符 | `/order/delete/{uuid}` |
| `case_type` | 用例类型（**注意**：不是 `type`） | `正向` / `逆向` / `边界` / `安全` / `业务流程` |
| `desc` | 测试描述（**注意**：不是 `description`） | `用有效ID查询订单详情` |
| `params` | 请求参数对象，GET/DELETE 对应 Query，POST/PUT 对应 Body | `{"uuid": "xxx"}` |
| `headers` | 请求头（通常含 mobile 鉴权） | `{"mobile": "15251506890"}` |
| `expected_desc` | 预期结果描述（**注意**：不是 `expected_keyword`） | `HTTP 200，接口成功` |
| `expect_fn` | 智能判定函数（可选，不填则默认用 HTTP+biz 双判） | `exp_biz_fail` |

> ⚠️ **常见错误**：`type` 应为 `case_type`，`description` 应为 `desc`，`expected_keyword` 应为 `expected_desc`，否则脚本读取不到字段导致 Excel 表格为空。

### 3.3 期望函数详解（核心规则）

**期望函数选择决定了测试结果的准确性，是用例设计中最关键的环节。**

#### 3.3.1 四种基础期望函数

| 场景 | 期望函数 | 判定逻辑 |
|------|---------|---------|
| 正向测试：正常参数期望成功 | 不填（默认 exp_ok） | `http==200 && biz==200` → PASS |
| 逆向测试：缺参/空参/错误数据期望失败 | `exp_biz_fail` | `http==200 && biz!=200` → PASS |
| 边界测试：超长/极端值 | 不填（默认 exp_ok） | `http==200 && biz==200` → PASS；也接受 biz!=200（业务自行判断） |
| 安全测试：SQL注入/XSS期望被拦截 | `exp_biz_fail` | `http==200 && biz!=200` → PASS（攻击被拦截=业务失败） |

#### 3.3.2 expect_fn 选择示例

```json
// ✅ 正向测试 - 不填期望函数，默认 exp_ok
{
  "desc": "正常参数查询",
  "expect_fn": "",
  "expected_desc": "HTTP 200，返回数据"
}

// ✅ 逆向测试 - 缺少必填参数，用 exp_biz_fail
{
  "desc": "缺少必填参数uuid",
  "expect_fn": "exp_biz_fail",
  "expected_desc": "缺少必填参数uuid"
}

// ✅ 安全测试 - SQL注入攻击，用 exp_biz_fail
{
  "desc": "SQL注入攻击",
  "expect_fn": "exp_biz_fail",
  "expected_desc": "SQL注入被拦截"
}

// ❌ 安全测试错误用法 - exp_contains 可能失败（msg为空时）
{
  "desc": "SQL注入攻击",
  "expect_fn": "exp_contains:注入",  // 错！msg可能为空导致判断失败
  "expected_desc": "SQL注入被拦截"
}
```

#### 3.3.3 exp_contains 使用场景

| 场景 | 示例 | 说明 |
|------|------|------|
| 期望特定错误消息 | `expect_fn: "exp_contains:订单不存在"` | 消息中必须包含"订单不存在" |
| 资源不存在判定 | `expect_fn: "exp_contains:不存在"` | 消息中必须包含"不存在" |

> **重要**：如果安全测试的期望是"被拦截"，用 `exp_biz_fail` 而不是 `exp_contains`。因为被拦截时 msg 可能为空（`biz=500` 且 `msg=""`），`exp_contains` 会因为找不到关键字而失败。

### 3.4 参数设计规范

#### 3.4.1 必填参数绝不能为空

| 接口类型 | 常见必填参数 | 常见错误 |
|---------|------------|---------|
| GET详情 | `uuid`, `id`, `uuid` | `params = {}` |
| POST创建 | 请求体body | `params = {}` |
| DELETE | `uuid`, `fileId` | path占位符 `{uuid}` 未替换 |
| POST流程 | `uuid` | `params = {}` |

```json
// ❌ 错误：GET详情接口，uuid为空
{
  "method": "GET",
  "path": "/contractPreAudit/getById",
  "params": {}
}

// ✅ 正确：作为逆向测试，期望参数缺失被拦截
{
  "method": "GET",
  "path": "/contractPreAudit/getById",
  "params": {},
  "case_type": "逆向测试",
  "expect_fn": "exp_biz_fail",
  "expected_desc": "缺少必填参数uuid"
}
```

#### 3.4.2 DELETE接口路径格式

| 格式 | 示例 | 说明 |
|------|------|------|
| path参数型 | `/contractPreAudit/delete/{uuid}` | uuid在path中，params可为空 |
| query参数型 | `/contractPreAudit/deleteExternalFile` | uuid在query中，需 `params: {"fileId": "xxx"}` |

```json
// ✅ path参数型：path中已包含uuid
{
  "method": "DELETE",
  "path": "/contractPreAudit/delete/{uuid}",
  "params": {}
}

// ✅ query参数型：必须传参
{
  "method": "DELETE",
  "path": "/contractPreAudit/deleteExternalFile",
  "params": {"fileId": "test_fileId", "contractPreAuditId": "test_id"}
}
```

#### 3.4.3 POST/PUT请求必须有请求体

```json
// ❌ 错误：POST但params为空
{
  "method": "POST",
  "path": "/contractPreAudit/saveContractPreAudit",
  "params": {}
}

// ✅ 正确：逆向测试，期望缺少请求体被拦截
{
  "method": "POST",
  "path": "/contractPreAudit/saveContractPreAudit",
  "params": {},
  "case_type": "逆向测试",
  "expect_fn": "exp_biz_fail",
  "expected_desc": "缺少必填参数或请求体"
}
```

### 3.5 常见失败原因与修正

| # | 原因 | 修正方法 |
|---|------|---------|
| 1 | 期望函数用错（如安全测试用 exp_contains） | 安全测试统一用 `exp_biz_fail` |
| 2 | 必填参数缺失（uuid、body等） | 逆向测试不填参数用 `exp_biz_fail`；正向测试必须填参数 |
| 3 | DELETE路径格式错误 | 确认是path参数还是query参数 |
| 4 | 安全测试缺少必要参数 | 安全测试也要传必填参数，只改攻击字段 |
| 5 | 期望与实际业务不符 | 边界测试允许 biz=200 或 biz=500，取决于业务 |

### 3.6 缺陷等级定义

| 等级 | 定义 | 示例 |
|------|------|------|
| **P0** | 严重（安全漏洞） | SQL注入、XSS、路径遍历 — 立即修复 |
| **P1** | 高危（校验缺失） | 必填字段未校验、负数金额、鉴权失效、空字符串 |
| **P2** | 中等（边界处理） | uuid异常、pageSize边界、静默成功 |
| **P3** | 低危（功能兼容） | 字段格式兼容、mobile格式、比例超限 |

### 3.7 预期结果撰写规范

**核心原则：预期结果必须明确无歧义，禁止使用"或"连接多个可能结果。**

| 输入类型 | 预期结果写法 | 示例 |
|---------|------------|------|
| **合法输入** | `HTTP 200，{具体成功描述}` | `HTTP 200，接口成功` |
| **合法边界值** | `HTTP 200，{描述}` | `HTTP 200，接口成功（最小长度属于合法输入）` |
| **非法输入**（缺参、空串、类型错误） | `HTTP {错误码}，{错误提示}` | `HTTP 500，缺少必填字段` |
| **非法边界值**（超长、负数、格式错误） | `HTTP {错误码}，{错误提示}` | `HTTP 500，超出长度限制` |
| **鉴权失败** | `HTTP {错误码}，`（无mobile时） | `HTTP 500，` |
| **资源不存在** | `HTTP 200，{空数据描述}` | `HTTP 200，data为null` |
| **安全测试** | 明确说明期望的安全行为 | `HTTP 500，SQL注入未防护` |

**禁止写法：**
- `HTTP 200或500`（歧义）
- `可能返回成功或失败`（歧义）

**正确写法：**
- 合法输入 → `HTTP 200，接口成功`
- 非法输入 → `HTTP {错误码}，缺少必填字段`
- 不存在 → `HTTP 200，data为null`

### 3.8 用例数量分配参考

| 接口 HTTP 方法 | 建议用例数 |
|---------------|-----------|
| POST（创建） | 18-25 条 |
| PUT（更新） | 15-20 条 |
| GET（详情） | 8-12 条 |
| GET（列表） | 10-15 条 |
| DELETE | 6-10 条 |

**单接口用例类型推荐比例（专业版）：**

| 类型 | 比例 | 说明 |
|------|------|------|
| 正向 | 25% | 正常流程，验证核心功能 |
| 逆向 | 40% | 参数错误、数据不存在、权限问题 |
| 边界 | 20% | 极端值、空、null、超限（与逆向有重叠可精简） |
| 安全 | 15% | 注入、XSS、越权、敏感数据暴露 |

**⚠️ 重要规则：每个接口必须覆盖全部四种用例类型**

> 设计用例时，**必须对所有接口逐一检查**，确保每条接口都有正向、逆向、边界、安全四类用例。不能只重点测核心接口而遗漏查询类、辅助类接口。

### 3.9 业务流程（多接口串联）用例设计

**目标：** 从真实用户视角把多个接口串起来，验证完整业务链路是否闭环。

**设计步骤：**

1. 阅读 `input/` 中的需求文档，摘出**业务流程描述**章节
2. 把每一步拆成可调用接口，标注每一步依赖前一步的哪些输出（如 `uuid`、`procId`）
3. 为每条流程定义正向链 + 至少 1 条异常分支

**用例字段规则：**
- `api_name`：填**实际接口中文名称**（与 Apifox summary 一致）
- `case_type`：填 `业务流程`（由脚本识别）
- `desc`：填 `StepX: 操作描述`
- 步骤间依赖通过 `$变量名` 传参

**JSON 示例：**
```json
[
  {
    "api_name": "创建订单",
    "method": "POST",
    "path": "/order/create",
    "case_type": "业务流程",
    "desc": "Step1: 创建订单",
    "params": {"orderName": "自动化测试订单", "amount": 50000},
    "expected_desc": "HTTP 200，接口成功"
  },
  {
    "api_name": "查询订单",
    "method": "GET",
    "path": "/order/getById",
    "case_type": "业务流程",
    "desc": "Step2: 用上一步创建的uuid查询详情",
    "params": {"uuid": "$uuid"},
    "expected_desc": "HTTP 200，接口成功"
  },
  {
    "api_name": "删除订单",
    "method": "DELETE",
    "path": "/order/delete/{uuid}",
    "case_type": "业务流程",
    "desc": "Step3: 删除刚才创建的订单",
    "params": {"uuid": "$uuid"},
    "expected_desc": "HTTP 200，接口成功"
  }
]
```

**业务流程注意事项：**

| 规则 | 说明 |
|------|------|
| 每个步骤单独一个用例 | 不能把所有步骤合并成一个用例 |
| api_name 填实际接口名 | 不要填整条流程的名称 |
| case_type 统一填"业务流程" | 用于脚本识别流程用例 |
| 步骤描述用 StepX 开头 | 如 "Step1: 创建订单" |
| DELETE接口确认参数类型 | path参数型 vs query参数型 |

**业务流程执行原则：**
- 任一前置步骤失败，后续步骤不应阻塞整个测试
- 数据必须可回收：正向流程末尾应带删除步骤
- 异常分支独立于正向分支，不得互相影响

### 3.10 用例设计检查清单

执行测试前，逐项检查用例：

- [ ] 正向测试有完整必填参数
- [ ] 逆向测试用 `exp_biz_fail`
- [ ] 安全测试用 `exp_biz_fail`（不用 `exp_contains`）
- [ ] DELETE接口确认是path参数还是query参数
- [ ] POST/PUT请求有请求体（逆向测试除外）
- [ ] 业务流程每步用正确的接口
- [ ] 业务流程步骤间参数传递正确（`$uuid`）

## 四、测试数据规范

### 4.1 测试数据准备原则
- **独立性**：每个用例的数据不依赖其他用例的执行结果
- **可重复**：数据可反复创建和清理，不污染环境
- **真实性**：使用接近生产环境的数据结构和业务含义
- **隔离性**：测试环境与生产环境数据隔离

### 4.2 测试数据分类管理
| 数据类型 | 说明 | 生命周期 |
|---------|------|----------|
| **固定桩数据** | 固定的 uuid/fileId，用于冒烟验证 | 长期有效 |
| **动态数据** | 每轮测试新建、测试后清理 | 单次测试周期 |
| **Mock 数据** | 后端未就绪时，用 Mock Server 模拟响应 | 开发阶段 |

### 4.3 appCode 管理
- appCode 统一配置在 `config.ini`，不得硬编码在脚本中
- appCode 注入位置（Header / Query / Body）需在文档中明确记录
- 不同环境（测试 / 预生产 / 生产）使用不同的 appCode

## 五、测试执行原则

### 5.1 单接口 + 业务流程必须一次跑完

```bash
# ✅ 正确：一次执行所有用例
python run_test.py --output D:/test-output/项目名/

# ❌ 错误：分开执行会导致：
# 1. 业务流程数据断裂（uuid无法传递）
# 2. 报告时间戳不一致
# 3. 重复执行浪费时间
```

### 5.2 断点续跑

测试支持中断后从断点继续执行：

| 参数 | 说明 |
|------|------|
| `--resume` | 从上次中断处继续执行 |
| `--discard` | 放弃进度，重新开始测试 |

```bash
# 首次执行
python run_test.py --output D:/test-output/项目名/

# 测试中断后继续（自动检测到进度文件，5秒后自动续跑）
python run_test.py --output D:/test-output/项目名/

# 强制继续
python run_test.py --output D:/test-output/项目名/ --resume

# 放弃进度，重新开始
python run_test.py --output D:/test-output/项目名/ --discard
```

**限制**：
- 业务流程必须整体执行（不能从中间步骤续跑）
- 续跑时会跳过已完成的用例，不重复执行

### 5.3 测试结果分析步骤

1. 先看通过率，初步判断
2. 分析 FAIL 用例的原因
3. 区分：测试设计问题 vs 真实bug
4. 真实bug按缺陷等级分类

### 5.4 快速判断bug真假

| 现象 | 可能原因 | 判断方法 |
|------|---------|---------|
| biz=500 + msg="数据库操作异常" | 接口字段不匹配、数据库约束 | 可能是真实bug |
| biz=500 + msg="Required request parameter..." | 参数缺失 | 测试设计问题 |
| 安全测试 biz=200（攻击被接受） | 未做安全过滤 | **真实P0问题** |
| 业务流程全PASS | 核心链路正常 | 功能基本可用 |

## 六、接口测试整体流程

```
1. 获取接口文档   →  Apifox / Swagger / OpenAPI 规范
2. 阅读需求文档   →  input/*.docx，摘出业务流程章节
3. 分析接口定义   →  请求参数、响应结构、鉴权方式
4. 设计测试用例   →  单接口：正向+逆向+边界+安全；业务流程：多接口串联
5. 准备测试数据   →  固定桩数据 + 动态数据（带时间戳避免污染）
6. 执行测试       →  Python 脚本批量执行，记录 HTTP 状态、接口响应状态、响应关键字
7. 分析测试结果   →  按 PASS/FAIL 分类，按失败类型聚合问题
8. 生成测试报告   →  Excel（单 Sheet 10 列）+ Word（6 章节），时间戳一致
9. 缺陷跟踪       →  失败用例转缺陷单，跟踪修复
10. 回归验证      →  修复后重跑同一份脚本，对比历史 JSON 验证回归
```
